# 平台象棋规则

本文按当前代码说明实际运行规则，核对环境为python-chess1.11.2。平台没有另造棋子走法：它用标准`chess.Board`校验普通国际象棋动作。**与完整线下竞赛规程的主要差异在和棋触发、计时、非法动作处置和比赛管理。**这份文档描述现有行为，不表示所有限制都已修复。

裁判依据为[Game](../chessarena/core/game.py)，网络提交策略为[Session](../chessarena/web/session.py)，联赛统计为[league.py](../chessarena/league.py)。如未来代码改变，应同步更新本文。

## 1 棋盘、颜色与轮次

棋盘为8×8，纵列`a–h`，横线`1–8`。白先，每个成功动作后轮到另一方。白方棋子用大写`PNBRQK`，黑方用小写`pnbrqk`。

标准初始FEN：

```text
rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1
```

平台把一方走一次称为一个**半步**，`ply`统计从本次起点后的成功半步数。白黑各走一次才是通常说的一个完整回合。自定义FEN的`fullmove_number`不一定与平台ply一一对应。

学生矩阵固定按第8横线到第1横线排列；浏览器翻转不会改变数据坐标。训练和比赛没有战争迷雾，双方可以读取完整当前局面和成功动作历史。

## 2 棋子走法

实际合法性由`candidate in self._board.legal_moves`决定，包含以下通常规则：

| 棋子 | 行走和吃子 |
|---|---|
| 王K/k | 横、竖、斜走一格；不能进入受攻击格，双方王不能相邻 |
| 后Q/q | 横、竖、斜任意格，不能越子 |
| 车R/r | 横、竖任意格，不能越子 |
| 象B/b | 斜线任意格，不能越子 |
| 马N/n | 一格加两格的L形，可越过中间棋子 |
| 兵P/p | 白向横线增大方向、黑向横线减小方向；前进一步不吃子，从起始横线可前进两格但路径须空，斜前一格吃敌子 |

不能吃己方棋子，不能以任何动作让己王保持或进入受将。王不会作为普通被吃棋子被吃掉；目标是将死。

“受将”不等于“已经失败”。受将时可以移王、吃掉将军棋子、挡住攻击等，只要动作符合完整规则并消除王受攻击状态。

## 3 特殊走法

### 3.1 王车易位

使用标准国际象棋易位，不是Chess960。UCI提交的是王的移动：白王翼`e1g1`、后翼`e1c1`；黑方`e8g8/e8c8`。

必须保有对应易位权，相关棋子和路径符合规则，王当前不能受将，也不能穿过或落在受攻击格。仅凭王和车仍在起始格不足以判断能否易位，因为它们此前可能移动过；学生应使用`castling_rights`或完整FEN。

### 3.2 吃过路兵

敌兵从起始位置前进两格后，符合条件的己兵可以在紧接着的回合斜吃到它经过的目标格。仍使用普通来源/目标UCI，例如`e5d6`。

平台保存原始FEN的EP目标，即使当前没有可合法执行的吃过路兵。目标字段存在不是合法动作保证；吃过路兵如果暴露己王受将，也不能提交成功。

### 3.3 升变

兵到达最后一横线必须选择后、车、象或马，UCI后缀分别为`q/r/b/n`，例如`a7a8n`。不允许变成王或兵。省略升变后缀不会自动升后，通常返回非法动作。前端的四选一只是生成提案，最终仍由裁判检查。

## 4 提交与裁判

正常动作从`submit()`进入，主要检查顺序为：对局是否终局、UCI格式、绑定颜色是否轮到、动作是否在规则库合法动作中。HTTP会话在此前还检查选手类型、side与暂停状态。

成功时裁判修改棋盘、追加历史、清空错误、切换轮次，并检查终局。失败不会改变棋子、轮次或成功历史，但会记录错误和拒绝事件。错误提示不会给出一份替代合法动作列表。

只接受小写UCI，不接受SAN、`O-O`、跳过回合或`0000`。具体错误码见[API调用规范](API调用规范.md)。当前同起终点如`e2e2`会抛解析异常，未规范化为错误码；这是输入处理缺口，不是允许空走。

页面点击来源格或开始拖动不构成已经完成的棋步；平台不模拟线下的触子必走、按钟、裁判申诉或给对方加时等程序。非法提案采用本平台的返回码和重试机制，不能直接套用线下赛事的非法着法处罚流程。

## 5 棋规终局：实际检查顺序

创建对局、重置后以及每次成功落子后检查终局，优先级如下：

| 顺序 | 调用条件 | over_reason | result |
|---|---|---|---|
| 1 | `is_checkmate()` | `checkmate` | 被将死方负 |
| 2 | `is_stalemate()` | `stalemate` | `1/2-1/2` |
| 3 | `is_insufficient_material()` | `insufficient` | `1/2-1/2` |
| 4 | `is_repetition(3)`或`is_fivefold_repetition()` | `threefold` | `1/2-1/2` |
| 5 | `is_seventyfive_moves()`或`is_fifty_moves()` | `fifty` | `1/2-1/2` |

将死先于计数和棋判断，不能仅看到计数到阈值就自行给出和棋奖励。对局结束后继续提交返回`-4`。

### 5.1 将死与逼和

将死：当前方受将且没有合法应对，当前方负。逼和：当前方没有合法动作但未受将，双方和棋。

### 5.2 子力不足

平台调用python-chess的子力判定，例如王对王、王加单象对王、王加单马对王等可直接终局。具体采用库的算法，不是“无法强制获胜就判和”。例如双马对单王并不会仅因双马通常不能强制将死而被该检测自动认定为子力不足。

该检测不穷举所有可能行棋序列，也未接入残局表。某些由封锁局面形成的死局，即使任何合法序列都不能将死，也不一定被当前子力检测识别；平台没有另一个完整死局证明器。

### 5.3 三次重复：平台自动判和

相同局面实际出现三次后自动终局，不需要学生申请。重复判断不是只比棋子矩阵，还涉及走子方、易位权和有意义的吃过路兵机会，由python-chess维护历史判断；重复出现不必连续。

平台不提供“下一步将导致第三次重复，提前申请和棋”的接口，只检查已经形成的局面。第三次已自动结束，正常对局不会再等到第五次；代码保留五次重复的兜底分支，但原因仍标为`threefold`。

例如初始局面后执行：

```text
g1f3 g8f6 f3g1 f6g8 g1f3 g8f6 f3g1 f6g8
```

最后一步之后第三次回到初始布局和轮次，自动三次重复和棋。

### 5.4 50步规则：平台自动判和

`halfmove_clock`达到100半步，即双方各50步未走兵且未吃子，并满足库的相应条件时，平台自动和棋，不需申请。走兵或吃子会重置该计数。

平台不支持“预报下一手将达到50步并申请和棋”。75步分支也保留，但正常比赛通常已在50步自动结束；原因统一记为`fifty`。

### 5.5 与FIDE和棋程序的区别

FIDE规则第9.2/9.3条的三次重复和50步通常依赖有效申请，并允许声明即将形成该条件的动作；第9.6条规定五次重复与75步自动终局。本平台省略申请程序，直接对已经形成的三次重复与50步自动判和，也不提供协议和棋接口。[FIDE规则原文](https://handbook.fide.com/chapter/e012023)

这意味着训练奖励与比赛结束时机应遵循平台状态，不能直接把本地规则库`is_game_over(claim_draw=False)`当作平台终局。当前FEN也无法单独恢复平台已经判定的重复和棋或程序判负。

## 6 非棋规终局与AI提交规则

| over_reason | 默认行为 |
|---|---|
| `resign` | 指定方认输，对方胜 |
| `forfeit` | 自动Agent返回None等，当前方弃权负 |
| `error` | 自动Agent思考时抛普通异常，当前方负 |
| `timeout` | 自动Agent超过本步预算，当前方负 |
| `retry_exhausted` | 自动Agent的失败重试用尽，当前方负 |

认输、弃权和程序处置直接生成对方胜结果。没有FIDE计时规则中“对手不可能通过任何合法序列将死则超时和棋”的额外检查；当然，若之前已被子力不足判和，就不会再进入正常思考回合。FIDE相关计时规定见第6.9条。[FIDE规则原文](https://handbook.fide.com/chapter/e012023)

### 6.1 每步预算

默认3秒，控制的是当前一次自动决策回合，不是整局总时钟，不提供加秒或累积剩余时间。所有尝试共享截止时间，每次重试不会重置3秒。模型加载和TorchAgent预热在开局阶段，不计入逐步思考。

普通学生选手通过守护线程调用，超时后不等待它完成，但Python线程不会被强制终止。同一次思考上下文在超时/结束后继续提交会被拒绝；该机制不是进程资源隔离。

内置快路径选手`fast_local=True`在当前线程执行，返回后才核对耗时；学生不得通过设置此标志绕过普通计时路径。页面调速只影响展示间隔，不增加思考时间。

### 6.2 重试次数

`max_retries=3`表示首次失败后再允许3次：第1、2、3次被拒可以再试，第4次失败触发处置。实现条件是`attempts > max_retries`。设为0时，首次失败便处置。

普通自动Agent被拒后，驱动器会重新调用`choose_move()`；最新State携带`last_error`。平台驱动的HTTP服务遇到可重试网络错误等，也会占用次数和剩余时间。

学生若在一次`choose_move()`内自己循环调用`submit()`多次，裁判会记录每次动作错误，但驱动器的尝试计数按返回轮次统计，不会对循环中的每次提交分别递增；时间预算仍继续。这是当前计数边界。推荐每次调用只提出一个动作并返回Result。

### 6.3 随机替走策略

`on_timeout`、`on_retry_exhausted`可以分别设为`random`。此时平台从真实合法动作中随机选择一手替走，经裁判提交后继续，而不是判负。这属于教学容错策略，不代表网络的决策。

普通异常和返回None仍直接判负，不走随机替代。正式比较模型应固定两项策略为`forfeit`。

### 6.4 不同接入方式的差异

| 接入方式 | 计时与重试 |
|---|---|
| 平台驱动`agents/*.py` | 执行上述预算和重试 |
| 平台驱动`http:名字/uci:名字` | 外部调用同样受裁判预算与适配器超时约束 |
| 网页人类 | 不经过自动Agent步时循环；没有默认3秒手动落子判负 |
| 主动HTTP的`api`选手 | 等待学生请求；当前不累计每步预算或拒绝次数判负 |
| 训练器直接`Player.submit()` | 仅该次动作检查；训练器自行安排计时与循环 |
| 终端`HumanAgent` | 不累计非法尝试；阻塞输入不会被普通工作线程强制中断，返回后才可能检查超时 |

因此不能把主动API选手和自动Agent不加区分地纳入严格等时比赛。

## 7 自定义FEN、重开与悔棋

平台可以从自定义FEN开局，但目前只调用`chess.Board(fen)`解析，没有额外调用`is_valid()`检查局面在棋规上的完整有效性。FEN语法可解析不代表局面可由合法对局到达；教师提供测试残局时应自行验证，不要用缺王或其他异常局面评分。

FEN不能携带重复历史。以一个中局FEN重新开局，之前发生过几次相同局面不会被恢复；成功动作历史从新起点重新累计。FEN的半步计数会保留，可导致开局即满足50步等条件。

创建或重置至已终局的有效局面会立即设置结果。`reset()`清空本局成功历史，通常保留game_id，不重新调用Agent开局钩子；`new`则重新装配选手。悔棋可以恢复终局前状态，重新允许继续。

这些管理操作是教学功能，不是正常竞赛棋规动作；正式比赛不应让参赛程序调用它们。当前管理端点无账号认证，Python选手也不是安全沙箱；只读棋盘接口是程序设计边界，不是完整防作弊系统。

## 8 半步上限、联赛统计与评分限制

`Game.run_to_end(max_plies=...)`达到上限仅停止推进，不自动判和；若尚未终局，`game.result`为None，PGN结果为`*`。CLI的play默认400半步并以退出码3表示未完成，联赛默认600半步。

当前联赛有以下实现口径：

- 随机开局步数是半步，动作由平台代走并计入history/ply。
- `score_of("*")`返回0.5；未完成或部分异常记录可能被双方各计半分并参与ELO更新。这不是裁判宣告和棋。
- 非法率来自该整局的拒绝次数除以整局成功半步与拒绝数之和；同局数据累计到双方，不能判定是哪一方非法。
- 平均每步时间用整局耗时除以半步数；整局耗时可能包含模型初始化与双方开销，不等于单个网络的纯前向耗时。
- CLI的`test`只把明确`1/2-1/2`计作和棋，`*`会落入失败统计，与league的半分口径不同。

正式课程评分需固定半步上限、随机开局、硬件、策略与超时条件，并检查`over_reason`和未完成记录。当前报告适合教学参考，不能仅凭显示的ELO、非法率或平均步时宣称完成严格公平排名。

## 9 规则复现示例

下面展示三次重复实际触发点。保存到仓库根目录运行：

```python
from chessarena import Arena

arena = Arena(live=False)
try:
    game = arena.new_game(white=None, black=None)
    moves = "g1f3 g8f6 f3g1 f6g8 g1f3 g8f6 f3g1 f6g8".split()
    for move in moves:
        player = game.player(game.turn)
        assert player.submit(move).ok
    assert game.result == "1/2-1/2"
    assert game.over_reason == "threefold"
    print(game.ply, game.result, game.over_reason)
finally:
    arena.close()
```

学生自行恢复本地历史的方法：

```python
import chess


def reconstruct_history(state):
    local_board = chess.Board(state.start_fen)
    for move in state.history:
        local_board.push_uci(move)
    return local_board
```

这只是学生自己的分析棋盘，不能修改真实棋盘。最终结束状态仍以平台`is_game_over/result/over_reason`为准。
